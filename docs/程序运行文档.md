```
Python 3.11，项目自带 .venv
依赖清单见 requirements.txt
```

```bat
cd C:\gyb-software\programs\program-pptcreator02
```

## 二、env 文件配置

### 2.1 加载规则

`src/pptgen/config.py` 自己解析 `.env`，不依赖 python-dotenv。有几条必须知道：

| 规则 | 说明 |
|---|---|
| 路径固定 | `项目根/.env`，不能用环境变量改 |
| 编码 | `utf-8-sig`，带 BOM 也能读 |
| 跳过 | 空行、井号开头行、不含等号的行 |
| 去引号 | 值两端的单引号与双引号会被剥掉 |
| **空值即未设置** | `KEY=` 整行被丢弃，代码走默认值 |
| 不支持 export | 写了 `export KEY=VALUE` 不会剥前缀 |
| **系统环境变量优先** | 同名键已存在于系统环境时，`.env` 里那份被静默忽略 |
| 优先级 | 默认不覆盖，全仓库没有以覆盖模式调用过 |

值的读取有三个访问器：`get` 对空串退回默认值，`get_int` 对非数字退回默认值，`get_bool` 只认 `1/true/yes/on` 与 `0/false/no/off`，其余退回默认。**都不报错。**

### 2.2 生效时机

`run.py` 在进程启动时读一次，每个子命令开头再读一次。`server.py` 只在 `main()` 与 `/api/config` 端点里读。

**运行中的服务不会重读 `.env`。改了配置必须重启进程，除了 `/api/config` 那个端点。**

### 2.3 文本模型

用于解析后的内容提炼、大纲生成、逐页规划、文案压缩、整页重做。任何 OpenAI 兼容的 `/chat/completions` 端点都可以。

```ini
PPTGEN_LLM_BASE_URL=https://api.deepseek.com
PPTGEN_LLM_API_KEY=sk-xxxx
PPTGEN_LLM_MODEL=deepseek-chat
```

三项必须齐全才算配置成功。缺任何一项都等同于没有配置模型，大纲与规划会走确定性兜底。

常见服务商填法：

| 服务商 | BASE_URL | MODEL |
|---|---|---|
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus` |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 阿里通义 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-max` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o` |
| 本地 vLLM | `http://localhost:11434/v1` | `qwen2.5:14b` |

Azure 的写法不同：`PPTGEN_LLM_API_VERSION` 填了就走 Azure 的 URL 与 `api-key` 请求头，不填就是标准 Bearer 鉴权。

### 2.4 视觉模型

用于看图验收。必须支持 base64 图片输入。

```ini
PPTGEN_VISION_BASE_URL=https://api.openai.com/v1
PPTGEN_VISION_API_KEY=sk-xxxx
PPTGEN_VISION_MODEL=gpt-4o
```

`PPTGEN_VISION_FALLBACK_TO_LLM` 默认 1。它的作用范围很窄：**只在给了视觉模型名、但没给 base 或 key 时**，复用文本模型的连接信息，模型名仍用视觉自己的。

有一份无视觉能力模型的黑名单，按名称前缀匹配：`deepseek-chat`、`deepseek-flash`、`deepseek-reasoner`、`deepseek-coder`、`gpt-3.5`、`text-davinci`、`o1-mini`。命中就直接判定为不可用，不发起调用。

设这个黑名单的理由是：不设的话调用会返回一堆无法解析的文字，看起来像看图通过了。

> **当前 `.env` 里视觉模型填的是 `deepseek-flash`，命中黑名单。所以本机的看图 QA 永远走人工复核包，不会调用视觉模型。** 要启用自动看图必须换一个真正支持图片的模型。

### 2.5 生成参数

| 变量 | 默认值 | 作用 |
|---|---|---|
| `PPTGEN_MIN_PAGES` | 13 | 正文页数下限，不含章节分隔页 |
| `PPTGEN_MAX_PAGES` | 18 | 正文页数上限，不含章节分隔页 |
| `PPTGEN_SECTION_DIVIDERS` | 1 | 是否插入章节分隔页。装不下就完全不插 |
| `PPTGEN_OUTLINE_SEGMENT` | 1 | 骨架分不出章时是否让模型归类。置 0 则完全离线 |
| `PPTGEN_CONTENT_MODE` | balance | `strict` 只做结构整理，`balance` 允许合并提炼，`enrich` 可补写过渡。非法值静默退回 `balance` |
| `PPTGEN_TIMEOUT` | 180 | 单次请求超时秒数 |
| `PPTGEN_RETRY` | 2 | 重试次数，总尝试次数为这个值加一 |
| `PPTGEN_MAX_TOKENS` | 8000 | 通用调用的输出上限 |
| `PPTGEN_OUTLINE_MAX_TOKENS` | 留空 | 大纲阶段输出上限。留空时取 `max(PPTGEN_MAX_TOKENS, 16000)` |
| `PPTGEN_PLAN_MAX_TOKENS` | 留空 | 单批规划输出上限。派生规则同上 |
| `PPTGEN_REVISE_MAX_PAGES` | 3 | 一次提交最多整页重做几页，下限 1 |
| `PPTGEN_TEMPLATE` | 迈胜PPT模板.pptx | 公司模板路径 |
| `PPTGEN_OUT` | out | 输出根目录 |

页数区间的下限与上限写反时会自动交换。

推理模型会把大量 token 花在推理上，`PPTGEN_MAX_TOKENS` 给小了会表现为正文为空。而正文为空会被兜底静默吞掉，看起来像大纲质量就是差。**建议不低于 8000。**

### 2.6 文件日志

| 变量 | 默认值 | 作用 |
|---|---|---|
| `PPTGEN_LOG` | 1 | 文件日志总开关。置 0 后所有日志方法变空操作 |
| `PPTGEN_LOG_DIR` | 留空 | 日志根目录。留空取 `PPTGEN_OUT/logs` |
| `PPTGEN_LOG_MAX_COPY_MB` | 64 | 超过这个大小的源文件与成品只记路径与 sha256，不复制 |
| `PPTGEN_LOG_PPTX` | copy | 成品 pptx 是否复制进日志夹。设 `none` 则不复制 |

### 2.7 预览渲染

| 变量 | 默认值 | 作用 |
|---|---|---|
| `PPTGEN_PREVIEW_WIDTH` | 1920 | 网页逐页预览图宽。1920 乘 1080 已是渲染上限 |
| `PPTGEN_PREVIEW_HEIGHT` | 1080 | 同上，高 |

**这两个值参与渲染指纹。改了会让旧的预览图全部失效并重渲一次。**

渲染耗时取决于 PowerPoint 起进程，与分辨率无关，所以调小只省磁盘不省时间。看图 QA 那一路固定 1280 乘 720，不受这两个值影响。

### 2.8 查看当前配置

```bat
.venv\Scripts\python.exe run.py config
```

输出九行：文本模型、视觉模型、页数区间、预览分辨率、章节分隔、内容策略、模板、输出目录、文件日志状态。日志关闭时会打印已关闭。

这个命令不产生日志文件夹。

### 2.9 排查配置不生效

按这个顺序查：

1. 变量名是否拼错，全部以 `PPTGEN_` 开头
2. `.env` 里是否写成了空值，空值等于没写
3. 系统环境里是否已有同名变量，**它的优先级高于 `.env`**
4. 服务是否忘了重启，运行期不重读 `.env`

## 三、启动与停止

### 3.1 网页方式

```bat
cd C:\gyb-software\programs\program-pptcreator02
.venv\Scripts\python.exe server.py
```

打开浏览器访问 `http://127.0.0.1:8000`。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--port` | 8000 | 端口 |
| `--host` | 127.0.0.1 | 绑定地址 |

启动时先读 `.env`，再创建六个输出目录，然后起一个多线程 HTTP 服务。启动横幅会打印访问地址与完整配置状态。

**停止方式只有 Ctrl+C。** 没有优雅关闭钩子，也没有关闭端点。所有长任务跑在守护线程上，主进程退出即随之结束，因此 Ctrl+C 会直接中断正在跑的任务。

**服务没有任何鉴权。默认只绑本机。** 改成 `--host 0.0.0.0` 等于把上传、下载与生成能力开放给整个网络，不要这么做。

静态文件服务三个目录：`web/` 下是前端三个文件，`out/visual/` 下是预览图，`out/samples/` 下是成品下载。路径都经过越界校验，防止目录穿越。

### 3.2 命令行方式

一条命令走完：

```bat
.venv\Scripts\python.exe run.py full --src "文档.pptx"          :: 做到大纲停下等确认
.venv\Scripts\python.exe run.py full --src "文档.pptx" --yes    :: 一路走完
```

分步执行：

```bat
.venv\Scripts\python.exe run.py parse   --src "文档.pptx"
.venv\Scripts\python.exe run.py outline --src "文档.pptx"
.venv\Scripts\python.exe run.py plan    --outline out\plans\文档.outline.json
.venv\Scripts\python.exe run.py build   --spec out\plans\文档.deck.json
.venv\Scripts\python.exe run.py qa
.venv\Scripts\python.exe run.py render
.venv\Scripts\python.exe run.py repair  --spec out\plans\文档.deck.json --rounds 3
.venv\Scripts\python.exe run.py revise  --deck out\plans\文档.deck.repaired.json --text "第5页标题压到10字内"
```

子命令清单：

| 子命令 | 必填参数 | 作用 |
|---|---|---|
| `config` | 无 | 打印配置状态 |
| `parse` | `--src` | 解析源文档，产出 `.parsed.json` |
| `outline` | `--src` 或 `--parsed` | 生成大纲，产出 `.outline.json` 与 `.outline.md` |
| `plan` | `--outline` | 大纲落到每页版式，产出 `.deck.json` |
| `build` | 无 | 渲染 pptx |
| `qa` | 无 | 几何检查与结构自检 |
| `render` | 无 | 渲染成图，并跑看图 QA |
| `repair` | `--spec` | 文案压缩的修复回环，默认 3 轮 |
| `revise` | `--deck` `--text` | 按页修改，**默认只打印方案，加 `--apply` 才落盘** |
| `all` | 无 | build 加 qa 加 render |
| `auto` | `--src` | parse 加 outline，停在大纲等确认 |
| `full` | `--src` | 一条命令走完 parse 到 render |

`qa` 与 `render` 省略 `--file` 时，自动取 `out/samples/` 下最新的 pptx。

`--content` 参数默认值是 `dify`，它走的是内置样例内容通道，**完全绕过解析与模型**，只用来自查版式渲染，不要用它处理真实文档。

`revise` 必须有文本模型，没配时直接失败。它刻意不学大纲与规划的兜底，因为出不了补丁的成功是最坏的静默失败。

## 五、log 文件夹记录逻辑

### 5.1 目录结构

每跑一次流程留一个自包含的文件夹：

```
out/logs/2026-09-22-15-46-文档名/
├── run.json                  关键值，增量落盘
├── run.log                   完整流水
├── 文档名.pptx                成品
└── 文档名.pdf                 源文件，仅上传来源才放
```

### 5.2 命名规则

目录名是 `<年-月-日-时-分>-<任务名>`。

时间戳是**流程启动时刻**，不是首次写日志的时刻，在日志对象创建时就冻结。

任务名的来源依次是：命令行 `--name`、修订命令的 deck 文件名、源文件或中间产物的文件名去掉阶段后缀、`qa` 与 `render` 跟随最新产物的文件名、最后兜底为 `run`。

任务名会做消毒：路径分隔符与通配符换成下划线，去掉首尾空格与点，Windows 保留名换成 `run`，**截断到 40 字符**。

**同名不覆盖。** 同一分钟内的同名任务靠逐个尝试创建目录来抢占，重名追加 `-2` 一直到 `-99`。多线程服务下并发任务不会互相覆盖。

目录只在第一次真正落盘时才创建。建不出来时打一条警告并把日志整体关掉，后续全部变空操作。

### 5.3 run.json

记四组，每个阶段结束增量落盘。

| 组 | 内容 |
|---|---|
| 运行基本信息 | 任务名、入口、命令、起止时间、耗时、是否成功、错误 |
| 源文档与结构 | 文件名、来源、字数、块数与块类型分布、骨架方法与章节树 |
| 各阶段质量与降级 | 每阶段耗时与成败、大纲是模型还是兜底、模型名、警告清单、版式分布、检查的 error 与 warn |
| 配置快照 | 页数区间、内容策略、模板名与模板 sha256、两阶段的 token 预算 |

配置快照是**白名单**，只记七项，刻意不导出环境变量，防止 API Key 泄露。

写盘是原子的：先写临时文件再替换。进程崩在写的中途也不会留下截断的、解析不了的 run.json，而那恰恰是最需要它可读的时刻。写入失败会回滚内存里的值，避免后续每一次写都失败、记录永久停在最后一个好版本。

### 5.4 run.log

行格式是 `[时:分:秒] 内容`，追加写入，**行缓冲**，崩溃时最后几行也留得下。

两个来源：

| 入口 | 方式 |
|---|---|
| 命令行 | 接管 stdout 与 stderr，按行攒后写入，退出时冲刷残留半行，因此异常堆栈也在日志里 |
| 网页 | 任务日志逐条写入，格式是消息加细节 |

控制台做了容错替换，而 run.log 是严格 UTF-8，**日志比控制台更完整**。

网页服务刻意不接管 stdout，因为那会把每一个 HTTP 请求都写进日志，并发任务会互相污染。

### 5.5 文件复制策略

| 内容 | 是否复制 |
|---|---|
| 上传的源文件 | 复制，超过 `PPTGEN_LOG_MAX_COPY_MB` 则只记路径与 sha256 |
| 根目录的源文件 | **不复制**，源本来就在仓库里 |
| 成品 pptx | 复制，`PPTGEN_LOG_PPTX=none` 时改记 sha256 |
| 中间产物 | 只复制 4MB 以内的 |

复制用保留时间戳的方式，目标名同样消毒。**同名绝不覆盖**，追加 `-2` 一直到 `-99`。源文件与成品常常同名，到底哪个是哪个，看 run.json 里的归档字段名。

Windows 上文件被渲染工具占着句柄时会重试三次，退避递增。

刻意不用硬链接，因为构建是原地截断写，硬链接会让下一次同名构建改掉已归档的历史产物。

### 5.6 作用域与续写

日志是线程局部的，**只有最外层建文件夹**，嵌套调用复用同一个。所以 `run.py full` 那条命令里串起来的各个阶段共用同一个日志文件夹。

网页的第二个请求可以续写同一个文件夹，续写时会读回旧 run.json 保留上一段数据，只覆盖命令与结束状态，并追加一次尝试记录。

Ctrl+C 与系统退出也会被记录，标成失败并留下异常名。

**所有落盘异常都被吞掉**，只在 stderr 打一条 `[runlog]` 前缀的警告。日志绝不拖垮流程。

### 5.7 排查流程质量

第一入口是 run.json 的三个字段：

| 字段 | 含义 |
|---|---|
| `outline.generated_by` | `llm` 或 `fallback` |
| `plan.generated_by` | `llm` 或 `fallback` |
| `render.mode` | `model` 或 `manual` |

出现 `fallback` 说明模型那一步没跑成，再看同组的 `warnings` 与 run.log 里的 `[outline] 模型调用失败` 或 `[plan] 模型规划失败` 行。

## 六、终端 log 打印逻辑

### 6.1 命令行前缀

输出按阶段打方括号前缀，纯文本无色：

| 前缀 | 内容 |
|---|---|
| `[parse]` | 文档标题与类型、块数与字数、块类型分布 |
| `[outline]` | 正文页数与目标区间、产物路径，随后打印整份大纲预览 |
| `[plan]` | 页数与产物路径、版式分布 |
| `[build]` | 产物路径、页数构成、结构自检结果 |
| `[repair]` | 开始与轮数、每轮的 error 与 warn 数、修正后的产物路径 |
| `[revise]` | 模式与预览图张数、逐页的改动明细、未能应用的条目的原因 |
| `[log]` | 日志文件夹绝对路径，收尾打印 |

这条收尾的 `[log]` 行**不会进 run.log**，因为它打印在日志接管范围之外，只在控制台出现。

模块内部也会往同一个出口写，例如预留分隔页预算、分批规划进度、模型调用失败退回兜底、文案超长被截断。

### 6.2 标记约定

| 标记 | 含义 |
|---|---|
| `[ERR ]` | 检查报告的 error 级问题 |
| `[warn]` | 检查报告的 warn 级问题，也用于日志自身的写盘失败 |
| `!` | 告警 |
| `✗` | 拒绝或失败 |
| `?` | 待澄清，用于修订时模型没能把条目对到具体页码 |
| `⚠️` | 兜底产物横幅，出现在大纲预览与网页上 |

几何报告的固定格式是：首行标题，第二行页数、画布与安全右边界，一条分隔线，逐条问题，末行合计。没有问题时打一行通过。

看图报告的两种形态：模型可用时逐页打印通过与不通过，不通过的附类别、问题与证据；模型不可用时打印人工复核包的联系表路径、评审提示词路径与单页图目录。

### 6.3 网页进度

网页的终端输出分两级：

**流水日志**，纯文本追加，进 run.log。

**进度项**，结构化的四色状态，在前端渲染成带点的条目：

| 级别 | 颜色 | 表现 |
|---|---|---|
| `info` | 灰 | 普通信息 |
| `active` | 红 | 正在执行，圆点循环跳动 |
| `warning` | 橙 | 需要注意 |
| `success` | 绿 | 已完成 |

**同时只允许一个活跃项。** 新的活跃项会把上一个降级为普通信息，任务收尾时把所有活跃项降级，避免最后那个点一直转。

前端每 1.2 秒轮询一次任务状态。

### 6.4 网页服务自身的输出

启动横幅打印访问地址、停止方式与完整配置状态。

每一个 HTTP 请求都会往 stderr 打一行两空格缩进的记录。任务线程里的未捕获异常会打印堆栈。

渲染清单写失败、续写文件失败、整份重渲的原因，都会打 `[warn]` 或 `[render]` 前缀的行。整份重渲的原因值得留意，它意味着这次要多花几分钟。

按 Ctrl+C 会打印一行已停止。

## 七、模型调用的超时、重试与降级

### 7.1 超时与重试

总尝试次数是 `PPTGEN_RETRY + 1`，默认 3 次。每次尝试独立计时，超时是 `PPTGEN_TIMEOUT`，默认 180 秒。

请求返回 4xx 时**立即停止重试**，只有 429 例外。其它异常继续重试。

退避是线性的：第一次失败后等 1.5 秒，第二次后等 3 秒。

**单次调用最坏耗时约 9 分钟**，即三次超时加两次退避。这个数字决定了几件事：规划阶段必须有分批进度日志，整页重做必须有页数上限。

### 7.2 空内容的识别

返回内容为空时会检查推理字段与推理 token 计数。命中则报一条明确的错误：模型只产出了推理内容，正文为空，推理占用了多少 token，建议把 `PPTGEN_MAX_TOKENS` 调大或换非推理模型。

**刻意不返回空串**，空串会让上游静默继续。

### 7.3 各阶段的降级行为

| 阶段 | 触发 | 行为 |
|---|---|---|
| 大纲 | 模型报错或结果为空 | 退回确定性大纲，标 `fallback`，打日志 |
| 大纲 | 未配置模型 | 同上，警告文案是未配置文本模型 |
| 规划 | 模型报错或结果为空 | 退回确定性规划，标 `fallback`，打日志 |
| 修复回环 | 未配置模型 | 跳过整个回环 |
| 修复回环 | 单页压缩失败 | 记录并继续下一轮 |
| 修复回环 | 达到轮数上限 | 停止并提示仍有未解决问题 |
| 整页重做 | 单页两次不合规 | 退回确定性生成，并把原因带回给用户 |
| 修订 | 未配置模型 | **不兜底，直接失败** |
| 看图 | 视觉模型不可用 | 输出人工复核包，不报错 |
| 渲染 | 原生渲染失败 | 退回默认渲染，并且必须回带分辨率参数 |
| 渲染 | 找不到渲染工具 | 跳过渲染，网页返回空图列表 |
| 日志 | 任何写盘失败 | 吞掉异常，只在 stderr 打一条警告 |

兜底的可见性贯穿整个项目。回退产物在大纲与规划里都带标记，会进 run.json、进大纲预览的横幅、进网页的告警框。以前它只打印一行 stdout，界面上和模型产出长得一模一样，结果就是拿着一份兜底大纲当模型产出看。

## 八、常见问题

**改了 .env 不生效。** 先查系统环境里有没有同名变量，它的优先级更高。再查服务是否重启过。

**跑完发现大纲质量很差。** 看 run.json 的 `outline.generated_by`。是 `fallback` 就说明模型那一步没跑成，看同组 warnings。

**模型调用很慢。** 单次最坏约 9 分钟。调小 `PPTGEN_TIMEOUT` 与 `PPTGEN_RETRY` 可以缩短上限，代价是网络抖动时更容易失败。

**正文页数不对。** 正文页数区间不含章节分隔页。关掉 `PPTGEN_SECTION_DIVIDERS` 可以省下这部分预算。

**生成出来正文是空的或很短。** 多半是 `PPTGEN_MAX_TOKENS` 给小了，推理模型把额度烧在推理上。建议不低于 8000。

**上传报读出来是密文。** 读文件的那个进程不是加密客户端信任的进程。换用 cmd.exe 把明文导出后再上传。

**网页上看不到预览图。** 检查 officecli 是否可用，`run.py config` 会显示。没有渲染工具时成品仍会正常生成。

**预览图不更新。** 渲染按页指纹缓存。指纹没变就不重渲。如果这一页内容确实变了却还是旧图，看服务日志里有没有渲染失败的行，渲染失败的页不会被记入清单。

**日志文件夹没生成。** 检查 `PPTGEN_LOG` 是否为 0，以及日志根目录是否可写。

**同一分钟跑了多次，日志目录带后缀。** 这是正常的重名抢占机制，依次追加 `-2` 到 `-99`。

**看图 QA 一直是人工复核包。** 当前视觉模型填的是不带图片能力的模型，命中黑名单。换一个真正支持图片输入的模型即可。
